## 问题：封面又少又乱

盘活博客的过程中，有个视觉问题一直硌着我：文章封面。

一开始的状态很糟：

- 所有文章的封面是从十来张图里**随机挑**的风景照
- 我新写的一批文章，封面几乎全堆在同一张 `code_dark.jpg` 上，重复得刺眼
- 主题配置里那套「随机默认封面」还挂着——它们走 CDN，URL 指向的是我**刚刚删掉的 `main` 分支**，全部 404

我想要的效果很明确：**每篇封面都不一样，而且和内容有关联。**

## 为什么不用图库照片

第一反应是去免费图库按主题找图。但很快撞墙。

技术文章的标题大多是抽象概念：「虚函数」「GC 原理」「排序算法」。这些东西**根本没有对应的实拍照片**。你搜到的无非是又一张笔记本电脑、又一片代码墙——放到「虚函数」上和放到「GC」上没有任何区别，等于没关联。

照片这条路，天然做不到「每篇唯一且和内容强关联」。于是换思路：**程序化生成。**

既然每篇文章都有标题、有分类，那就用这些信息**画**一张封面出来——分类决定配色，标题决定文字和细节。这样每张封面都是从文章数据长出来的，天然唯一，天然关联。

## 技术选型：SVG + headless Chrome

生成图片的方式很多，最后选了 **SVG**：

- 纯文本，用代码拼装最方便，改配色/布局就是改字符串
- 矢量，任意分辨率都清晰
- 无需重量级图形库

唯一的问题是 Butterfly 主题的封面用 PNG 更稳妥。所以流程是：**Python 拼 SVG → headless Chrome 截图转 PNG**。

用 Chrome 而不是专门的 SVG 光栅器，是因为它对中文字体和渐变滤镜的渲染和浏览器完全一致，所见即所得。脚本会自动探测本机的 Chrome / Chromium / Edge，Windows 本地和 Linux CI 都能跑：

```python
def find_chrome():
    env = os.environ.get("CHROME_BIN")
    if env and os.path.exists(env):
        return env
    for name in ("google-chrome", "chromium", "chromium-browser", "chrome"):
        path = shutil.which(name)
        if path:
            return path
    # 再兜底几个 Windows 常见安装路径
```

## 分类调色板：一套配色系统

第一版走的是「深色底 + 分类强调色」。每个二级分类一个颜色，定义在一张表里：

```python
PALETTES = {
    "Unity": ("#071b2b", "#160d2c", "#67e8f9", "#60a5fa", "#c084fc"),
    "C++":   ("#07142f", "#190c32", "#22d3ee", "#6366f1", "#f052d1"),
    "网络":   ("#042b2c", "#071735", "#34d399", "#22d3ee", "#3b82f6"),
    "算法":   ("#2b1705", "#1b0b31", "#fbbf24", "#fb7185", "#8b5cf6"),
    # ...
}
```

新增一个分类，就在这张表里加一行——这篇文章所在的 `AI探索` 专题，配色也是这么加进去的。

## 每篇唯一：让标题决定细节

光按分类配色还不够——同一个分类下十几篇文章，配色一样就会「像复制粘贴」。

解法是：**用标题的 hash 驱动画面细节。** 同一个标题每次算出来的结果是稳定的，但不同标题会得到不同的粒子位置、极光曲线弧度、轨道角度：

```python
def number(seed, start, end):
    """从标题 hash 稳定映射一个整数。"""
    return start + int(seed[:8], 16) % (end - start + 1)

seed = hashlib.sha256(title.encode()).hexdigest()
```

这样「C++ 虚函数」和「C++ 内存管理」配色同属一套蓝，但极光的走向、星尘的分布完全不同。同分类不撞图，同时又保持视觉家族感。

## 分类中景：一眼区分出主题

在统一的「极光 + 轨道 + 标题」骨架之上，再按分类切换一个**中景元素**，让不同领域一眼能分：

| 分类 | 中景 |
|------|------|
| C++ / C# | 全息轨道 |
| Unity / 图形学 | 棱镜碎片 |
| 网络 | 频谱波纹 |
| 算法 / 数据结构 | 节点关系图 |
| 计算机基础 / AI Coding | 电路结构 |
| 随笔 | 星轨 |
| 项目实战 | 玻璃拟态面板 |

骨架统一保证「是一套系统」，中景差异保证「一眼能分领域」。

## 一个真实的坑：辉光把字糊掉了

风格定下来后，我从远处看首页，发现一个问题：**标题特别糊，笔画糊成一团。**

排查下来，原因是我把霓虹辉光**直接套在了标题文字本体上**，还叠了左右偏移的青/粉色差层。在 1200×630 的原图上看着炫，一旦缩成首页的小卡片，笔画、辉光、色差就全糊在一起了。

这是典型的「设计只在大图上验收」翻的车。修法是把辉光和文字分离：

- 前景文字：高对比浅色渐变，**不加任何模糊**，再加一道细描边压住亮背景
- 辉光：单独放在文字**背后**一层，模糊半径也从 `11px + 3px` 砍到单层 `6px`
- 删掉左右色差副本
- 标题区域加一层弱暗色遮罩，压住背后极光的干扰

改完之后缩略图清晰了，炫酷的极光也还在。

> 教训很直接：**缩略图的可读性优先于大图的炫酷。** 封面大多数时候是以小卡片的形式被看到的，得在那个尺寸下验收。

## 保留真实截图的例外

不是所有封面都该被程序生成覆盖。

我有一篇讲 OpenGL 漫游系统的项目文章，封面是程序**真实运行的截图**——那才是最强的内容关联，没有任何生成图能替代。

所以脚本有一条铁律：**只处理没有手动指定 `cover:` 的文章。** 批量重刷时，加 `--all` 也只重绘自动生成的那些，永远不碰手动指定的真实截图。逻辑很简单，但保证了「自动化」和「手动例外」能共存。

## 落地到日常：一条命令

最后把这套东西固化进发布流程。现在我写完一篇文章，封面这一步只要：

```bash
bash scripts/new-cover.sh
```

它会扫描所有文章，只给**还没有封面**的那几篇生成 SVG、转 PNG、并把 `cover:` 字段写回 front-matter，已有封面的自动跳过。

关于要不要把这一步塞进 GitHub Actions（push 后云端自动生成），我们讨论后选了**本地生成**：图片直接进仓库、可预览、CI 零改动，代价只是我多跑一条命令。全自动方案要在 CI 里装 Chromium 和中文字体，复杂又易碎，对一个个人博客不划算。**能用简单方案稳住的，就别上复杂的。**

## 小结

这套封面系统最终做到了最初的目标：每篇唯一、和内容关联、风格统一、还能一键生成。

回头看，真正有价值的几个决定是：

1. **放弃图库照片**——抽象概念配不了实拍图，程序生成才能真正关联内容
2. **用数据驱动差异**——分类定配色，标题 hash 定细节，唯一性是算出来的
3. **在正确的尺寸验收**——封面是小卡片，可读性得在小卡片上过关
4. **给自动化留手动的口子**——真实截图这种例外，值得一条硬规则去保护

工具是 SVG 和几十行 Python，但让它真正好用的，是这几个判断。
