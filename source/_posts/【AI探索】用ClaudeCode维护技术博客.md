## 起点：一个跑不动的博客

我有一个基于 Hexo + Butterfly 的技术博客，托管在 GitHub Pages 上。它荒废了差不多一年——最后一篇文章停在去年 6 月，本地环境早就懒得动了。

这次我想把它重新盘活，但不想再手动折腾 `hexo new`、改配置、调主题。我想试的是另一件事：**把整个维护过程交给 Claude Code，我只做决策。**

这篇不是教程，是一次真实协作的复盘。我更关心的问题是：一个 AI 编码 Agent，到底能把这种「杂活」接到什么程度？哪些环节它做得比我快，哪些环节我必须踩刹车？

## 第一步：让 AI 先「读懂」这个项目

第一件事不是写代码，是让它熟悉现状。

Claude Code 扫了一遍仓库，很快给出了结论：这是 Hexo 生成的**静态产物**，仓库里没有 `_config.yml`、没有 `source/`，只有一堆预渲染的 HTML。也就是说，我 `main` 分支上看到的东西根本不是源文件。

它接着去翻远程分支，发现真正的源在 `source` 分支，而且那里有一份 `.cursor/rules` ——我很久以前写的项目规范。这份文件成了它的「说明书」：目录结构、新建文章的方式、分类规范、front-matter 模板、部署流程，全在里面。

> 这里得到的第一个经验：**给 AI 留一份项目规范文件（AGENTS.md / .cursor/rules 之类），比任何一次性的口头交代都值。** 它每次进来都能自己对齐上下文，不用我重新解释一遍项目长什么样。

## 分支治理：先把地基理清

摸清结构后，浮现出一个历史遗留问题——仓库里有三个分支：

```text
main       # 早期手动构建的 HTML 产物，内容停在一年前，没人用
source     # 真正的源文件（md、配置、脚本），我实际编辑的
gh-pages   # Actions 构建产物，线上服务真正读取的
```

`main` 是纯冗余，但它偏偏是默认分支，占着位。Claude Code 没有直接删——它先提醒我：删默认分支前得先把默认分支改成 `source`，否则会出问题。这个顺序它拎得很清楚：

```bash
# 1. 先改默认分支
gh api -X PATCH repos/<user>/<repo> -f default_branch=source
# 2. 再删除冗余分支
git push origin --delete main
```

**在不可逆操作上它是保守的**，会先说清风险和正确顺序，再等我确认。这一点比我预想的稳。

## 内容整理：从旧笔记到文章，以及一个隐私坑

博客荒了一年，但我手上其实攒了不少素材——一份实习期间记的技术笔记，2000 多行，混着面经、算法、Unity/C++ 知识点。

我让它把这份笔记整理成博客文章。它做的第一件事不是埋头写，而是**先和我对齐策略**：这批内容和我博客里已有的文章高度重叠（虚函数、内存管理、协程这些都写过），是全塞进去，还是只补没写过的？重叠的怎么处理？

这个「先问再做」的习惯省了我很多返工。最后我们只挑了博客真正缺的主题成文：排序算法、图与搜索、计算机基础、UGUI 源码解读、GC 原理等等。

但真正值得记的是**一个隐私坑**。

那份笔记里带了大量个人信息——真实姓名、具体公司名、面试话术。如果直接发出去，等于把自己的工作履历公开挂在网上。整理时它把这些全部剔除或做了脱敏处理，把具体雇主换成了中性表述。

更关键的是：脱敏不能只改「当前文件」。我后来意识到，**公司名早就散落在 git 提交历史里了**——某几条 commit message、几个历史版本的 md 都写过。公开仓库任何人翻 `git log` 都能看到。这个漏洞是 AI 主动指出来的，然后用 `git filter-repo` 把全部历史（包括 commit message）里的敏感词重写掉，强推覆盖。

```bash
# 重写全部分支历史里的敏感词，再强推
git filter-repo --replace-text replace.txt --force
```

> 这件事让我对「脱敏」的理解更完整了：**改文件只是表面，历史才是真正的暴露面。** 而这一步，我自己大概率会漏。

## 那些琐碎但烦人的修复

盘活一个老项目，一半时间花在这种小事上：

- **个人简介更新**——我换了工作状态，about 页和 GitHub profile README 都得改。顺带按我的要求做了脱敏（不写具体公司，只说方向）。
- **GitHub Stats 图崩了**——README 里那两张统计卡一直是裂图。它没瞎猜，直接 `curl` 测了下，返回 `503`：公共实例被限流，不是我的配置问题。于是换成了实测可用的 streak + 贡献图。
- **精选项目链接 404**——项目卡片里的仓库链接用户名写错了（少打了字母），点进去全是 404。顺手修了。

这些都不难，但一个人做起来又琐碎又容易漏。AI 的价值不在「难」，而在**它不会因为烦就跳过**。

## 自动化发布：把重复劳动固化下来

维护到后面，重复动作开始出现：写完 md → 生成封面 → 提交 → 推送 → 等构建。

我们把这套流程固化成了脚本和规范。现在我发一篇新文章只要三步：

```bash
# 1. 写好 md，放进 source/_posts/，front-matter 不用管封面
# 2. 一键生成封面
bash scripts/new-cover.sh
# 3. 提交推送，GitHub Actions 自动构建部署
git add -A && git commit -m "新增文章：xxx" && git push origin source
```

封面怎么自动生成的，是另一个足够写一篇的话题，我单独开了一篇讲。这里只说结论：**能固化成脚本的，就不该每次麻烦 AI**。AI 负责把流程设计出来、写成脚本、更新进项目规范；日常执行交给脚本，我一条命令搞定，AI 都不用在场。

## AI 接住了什么，我把关了什么

复盘下来，边界其实很清楚。

**AI 做得又快又好的：**

- 摸清陌生项目结构、从远程分支里找到真正的源
- 记住并执行既定规范（分类、front-matter、部署流程）
- 琐碎但成体系的修复（改链接、换图、批量整理）
- 主动发现我会漏的坑（git 历史里的敏感信息、CDN 限流的真实原因）
- 把重复流程沉淀成脚本和文档

**必须由我把关的：**

- **不可逆操作**——删分支、改写历史、强推，这些它会先停下来问，我也确实该逐条确认
- **隐私边界**——哪些算敏感、脱敏到什么程度，是我的判断，不是它的
- **内容取舍**——写什么、不写什么、专题往哪个方向走，这是我的博客，主线得我定

有意思的是，AI 最大的帮助不在「写得多快」，而在**它把我懒得做、或者根本想不到要做的环节补上了**。git 历史脱敏那一步，如果没它提醒，我这个博客现在还漏着。

## 一点感受

模型带来的是泛化能力——它能读懂一个它从没见过的项目，然后按我的规范干活。但这种能力默认是不稳定的，尤其在有副作用的操作上。

所以真正好用的用法，不是把方向盘全交出去，而是：**我定目标和边界，它跑执行和发现，遇到不可逆的地方它停、我拍板。** 中间那段——读项目、理分支、整内容、修琐碎、固化流程——它接得非常稳。

博客活过来了。而且比荒废之前更整洁：分支干净了、有了自动封面、有了发布脚本、有了这份还在长的项目规范。下一篇，我会专门讲那套自动封面系统是怎么从「随机风景图」一步步做到「每篇唯一且和内容关联」的。
